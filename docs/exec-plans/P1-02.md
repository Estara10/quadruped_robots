# P1-02 — Formal Experiment Contract

## Objective

Freeze and implement the formal experiment schema, validity rules, provenance contract, outcome precedence, and mechanically verifiable artifacts required for Phase 1 Acceptance evidence on Go2 + MuJoCo.

This task makes formal runs auditable; it does not claim an ABS performance result.

## Why

Existing simulation outcomes are `LEGACY / NON-ACCEPTANCE`: they lack a complete seed, event, collision, validity, and provenance contract. Without this task, later scenario and benchmark results cannot support Phase 1 Acceptance.

## Scope

1. Define one versioned formal-run schema and writer/validator contract.
2. Record run identity and provenance in a machine-readable manifest:
   - globally unique `run_id`, schema version, wall-clock and simulation/monotonic times;
   - Git commit, branch, dirty-state representation or patch hash;
   - deployed model names, paths and SHA-256 hashes;
   - effective controller/evaluator config snapshot and hash;
   - MuJoCo binary/version/timestep/solver data, Go2 MJCF/assets hash;
   - scenario ID/file/hash/obstacle metadata;
   - root seed and every declared downstream random source;
   - perception/ray source identity/version/hash; rates and outcome thresholds.
3. Implement machine-readable episode validity and `INVALID` reasons.
4. Define/write the minimum formal artifacts:
   - `manifest.json`;
   - telemetry with timestamp and sequence, pose/stability, policy/RA state, commands/velocity, Recovery values, ray validity, actions/targets/torques, collision/fall/arrival state;
   - `events.jsonl` for lifecycle, Recovery edges, collision edges, fall, arrival, timeout, invalidation and shutdown;
   - `summary.json` with validity, ordered outcome and primary metrics;
   - a fixed plot set: RA/switching, trajectory/obstacles, command tracking, roll-pitch-height, Recovery/switch markers.
5. Enforce safety-first outcome ordering: validity and collision/fall are evaluated before arrival; arrival requires an explicit hold with fresh valid telemetry.
6. Establish root-seed propagation and paired-comparison identity rules.
7. Enforce declared variants: `paper-faithful`, `stabilized`, and `agile-only`; results must remain stratified.
8. Add schema/fixture/replay tests and a validator that rejects incomplete or contradictory formal episodes.

## Out of Scope

- ABS paper review, model training, artifact provenance/order closure, or any claim that P1-01 is complete;
- RA, Agile, Recovery, switching, threshold, path-gain, speed, or solver changes;
- MuJoCo timing/dynamics freeze (P1-08);
- scenario-suite implementation and determinism study (P1-10);
- HUD/telemetry-product implementation beyond the minimum formal writer/reader boundary (P1-09);
- pilot, benchmark, Acceptance statistics, or real-robot execution;
- conversion of legacy runs into Acceptance evidence.

## Contract Details

### Episode validity

An episode starts `PENDING`, becomes `VALID` only after the protocol preflight events are present, and becomes `INVALID` on any required-contract violation. `INVALID` episodes are excluded from all Success/Collision/Fall/Timeout numerators and denominators, reported separately, and never silently retried.

Required invalid reasons include at minimum:

- missing, stale, malformed, wrong-run, or non-monotonic telemetry/events;
- controller not active or requested RL state never entered;
- collision telemetry unavailable under the registered definition;
- unknown/stale/invalid perception or ray source;
- missing or undeclared root/downstream seed;
- missing model/config/scene/binary hash or unresolved effective-config snapshot;
- startup failure, wrong hardware mode, or missing required lifecycle event;
- controller/evaluator goal or threshold disagreement;
- unsupported schema version or invalid outcome ordering.

### Outcome ordering

For each ordered sample/event boundary:

1. validate telemetry/event continuity and controller state;
2. process collision and fall transitions;
3. process timeout if no safety terminal outcome occurred;
4. evaluate goal-region occupancy and arrival hold only while valid, upright, and collision-free;
5. emit exactly one terminal outcome with its triggering sequence/time.

Collision or fall at a goal crossing vetoes Success. A terminal `INVALID` vetoes all performance outcomes.

### Paired variants and seeds

- A formal comparison declares an immutable scenario list and root-seed list before collecting formal outcomes.
- Each variant shares the same `(scenario_id, scenario_hash, root_seed)` tuple; the tuple plus config/model hashes forms the pairing key.
- Random sources must be named and either deterministically derived from the root seed or explicitly recorded as `UNKNOWN`, which invalidates the episode.
- Pilot seed lists and formal seed lists are disjoint and recorded.
- `paper-faithful`, `stabilized`, and `agile-only` are separate variant labels; aggregation across labels is prohibited by the validator.

## Implementation Steps

1. Locate current evaluator/scene/logging entrypoints listed below; map each required schema field to an authoritative runtime source or mark it `UNKNOWN`.
2. Add a schema version and canonical JSON serialization/hashing helpers; define forward-compatible required/optional fields.
3. Implement formal-run initialization that captures immutable provenance before controller launch/episode start.
4. Implement a single event emitter and ordered terminal-outcome reducer; prohibit text logs from serving as the event source.
5. Implement telemetry and summary writers with run-local paths and artifact links.
6. Implement seed registry/derivation recording and paired-variant key checks; do not yet create the P1-10 scenario suite.
7. Implement an offline validator that checks schema, hashes, sequence/time monotonicity, required events, validity, outcome precedence, and variant/seed pairing.
8. Add deterministic fixtures and regression tests; generate example `VALID` and each representative `INVALID` run without running a formal benchmark.
9. Document schema version, storage layout, validation commands, and migration rule: historical outputs remain `LEGACY / NON-ACCEPTANCE`.

## Mechanical Tests

| Test | Expected result |
|---|---|
| Manifest completeness/hash test | Missing required identity or altered snapshot/hash is rejected. |
| Event/telemetry ordering test | Duplicate or non-monotonic sequence/time is rejected. |
| Validity matrix test | Each required missing/stale/wrong-mode/controller/perception/collision/seed condition produces its specified `INVALID` reason. |
| Outcome precedence fixture | Collision or fall during goal crossing cannot emit Success; arrival hold only succeeds with valid safe samples. |
| Seed propagation fixture | Same declared root seed produces the same declared derived-source seeds and pairing key. |
| Pairing/variant test | Variants must share seed/scenario/hash; cross-variant aggregation is refused. |
| Artifact completeness test | Every `VALID` episode has manifest, telemetry, events, summary, and fixed plots with internal links. |
| Legacy classification test | Pre-contract/historical fixture is labeled `LEGACY / NON-ACCEPTANCE`, never `VALID`. |

## Acceptance Criteria

- Every formal episode can be classified mechanically as `VALID` or `INVALID` with one or more explicit reasons.
- `VALID` episodes contain all required identity, provenance, telemetry, events, summary, and fixed plot artifacts.
- Schema tests prove outcome safety precedence and rejection of corrupted/incomplete/mismatched runs.
- Seed lineage and paired-variant keys are recorded and mechanically verified.
- `paper-faithful`, `stabilized`, and `agile-only` data cannot be silently merged.
- Historical runs remain `LEGACY / NON-ACCEPTANCE`.
- No P1-01 `UNKNOWN` is relabeled as resolved, and no performance/Acceptance benchmark is run as part of P1-02 implementation.
- An independent Reviewer can reproduce the validator decision from saved fixtures and evidence.

## Reviewer Checklist

- Does every claimed required field have a runtime source, or remain explicitly `UNKNOWN`/`INVALID`?
- Are safety outcomes unambiguously ordered before arrival across event/sample ties?
- Can a caller bypass the validator or fabricate a `VALID` summary without raw links?
- Are root/downstream seeds, variants, scenario hashes and config/model hashes adequate to reproduce paired comparisons?
- Are P1-08/P1-09/P1-10 boundaries respected without prematurely freezing their work?
- Are legacy data and P1-01 provenance UNKNOWNs still clearly separated from formal evidence?

## Stop Conditions

- Stop and escalate to Director if the required schema would require changing algorithm semantics, thresholds, policy I/O, switching, solver, or safety strategy.
- Stop and record `UNKNOWN` if a required runtime field has no authoritative source; do not synthesize it.
- Stop before a benchmark, pilot, or real-robot run; those are later tasks with separate approval.
