Status: **ACCEPTED / COMPLETED** — offline paper-to-code traceability accepted by [independent review](../evidence/P1-03/REVIEW_2026-08-27_FINAL.md) on 2026-08-27. This is not paper-equivalence proof, runtime validation, benchmark evidence, or Phase 1 Acceptance.

## Objective

Create an evidence-backed, equation-by-equation mapping of the ABS paper specification to the training implementation, reference implementation, and runtime implementation. The result must distinguish `paper-faithful` behavior from explicitly documented `stabilized` engineering behavior without changing either implementation during this planning task.

P1-03 is a traceability task. It does not claim paper equivalence, experimental success, or Phase 1 Acceptance.

## Scope

1. Map the paper's declared runtime architecture and rates.
2. Map Agile observation/action equations, dimensions, scales, ordering, contact semantics and PD parameters.
3. Map ray count, angles, range, logarithmic representation and source geometry.
4. Map RA observation and target equations, discount factor, hindsight/softening, dataset-generation path and model architecture.
5. Map Recovery observation/action equations and safe-twist optimization, including Eq.21 and Eq.22.

## Evidence format for every equation/parameter

Each trace record must contain exactly these fields:

```yaml
id: ABS-EQ-<number>
kind: equation | parameter | architecture | semantic-rule
paper:
  source: docs/ABS_PAPER_NOTES.md or paper page/equation reference
  expression: <literal equation or parameter statement>
  variables: <ordered variable list and units>
training:
  path: <repository-relative path>
  symbol: <function/class/block>
  line_range: <stable line range at capture>
  expression_or_value: <literal implementation excerpt or value>
reference:
  status: PRESENT | ABSENT | NOT_APPLICABLE | UNKNOWN
  path: <path if present>
  symbol: <symbol if present>
runtime:
  path: <repository-relative path>
  symbol: <function/class/block>
  line_range: <stable line range at capture>
  expression_or_value: <literal implementation excerpt or value>
classification: MATCH | PAPER_FAITHFUL | STABILIZED_VARIANT | MISMATCH | UNKNOWN | CONFLICT
confidence: DIRECT_SOURCE | DERIVED_MECHANICALLY | CONDITIONAL | UNKNOWN
claims_not_made:
  - <explicitly excluded inference>
validation:
  fixture: <fixture path or NONE>
  method: <mechanical test description>
```

No record may close a claim using only a filename, comment, model filename, visual behavior or a non-immutable co-located file.

## UNKNOWN and conflict handling

- Missing source, unclear variable meaning, unavailable historical provenance or unresolvable implementation path is recorded as `UNKNOWN`.
- A disagreement between paper, training, reference and runtime is recorded as `CONFLICT` or `MISMATCH`; it is never silently normalized.
- `UNKNOWN` must include the missing artifact/symbol and the search boundary.
- Conflicting values must be listed separately with path, symbol, line range and hash where applicable.
- P1-01 provenance/order UNKNOWNs remain separate from formula comparison results.
- No value is promoted to `PASS`, `MATCH` or paper-faithful merely because a test fixture executes.
- If the evidence would require changing behavior to resolve it, stop and report the conflict rather than modify code.

## Paper-faithful / stabilized boundary

Every record must assign one of the following:

- `PAPER_FAITHFUL`: behavior directly specified by the paper and implemented without additional project engineering semantics.
- `STABILIZED_VARIANT`: an explicit engineering addition or deviation, such as path shaping, hysteresis, forced hold, extra clamping or changed optimization details.
- `MISMATCH`: implementation differs from the paper and is not yet classified as an accepted stabilized variant.
- `UNKNOWN`: evidence cannot establish the relationship.

The trace must preserve both formulas/values where they differ. It must not rewrite paper notes or reclassify a stabilized behavior as paper-faithful.

## Mechanical validation requirements

Add offline tests that do not launch runtime systems:

1. Every trace record has the required fields and a valid classification.
2. Every repository path and cited symbol exists.
3. Every cited line range contains the recorded symbol/value at capture.
4. Dimensions sum correctly for Agile 61-D, RA 19-D and Recovery 49-D contracts.
5. Units and parameter domains are explicit for rates, gains, scales, thresholds, ranges and horizons.
6. Paper-faithful and stabilized records are never merged into one classification.
7. A deliberate mismatch fixture is reported as `MISMATCH`, not `MATCH`.
8. A deliberate missing-source fixture is reported as `UNKNOWN`, not `PASS`.
9. Eq.22 independent reference arithmetic checks yaw-coupled and zero-yaw cases without changing runtime code.
10. Switching threshold and hold records preserve paper and stabilized values separately.
11. No test invokes ROS2, MuJoCo, benchmark, pilot, model export or real hardware.
12. Existing P1-02 tests remain green.
