## Objective

Connect authoritative runtime sources to the already-accepted P1-02 formal
contract (`abs-go2-formal-run/v1`), so that a future formal episode can bind every
required field to a real runtime producer rather than a fixture or `UNKNOWN`:

- run identity (`run_id`, schema version, wall-clock time, Git commit/branch/dirty
  state or dirty patch hash);
- effective config (snapshot + canonical hash, runtime-effective confirmation);
- seed lineage (root seed and every downstream random source, derived or
  explicitly `UNKNOWN`);
- simulation time (monotonic `simulation_time_s`, sequence, `telemetry_fresh`);
- ray source/mode and 11 rays (active `MUJOCO_RAY_SOURCE`, v2 header validity);
- structured safety events (controller active, RL entered, Recovery ENTER/EXIT,
  collision START/END, fall, arrival, timeout, invalidation, shutdown);
- 5×12 command chain (`action_raw`, `action_clipped`, `joint_target_rad`,
  `torque_nm`, `torque_saturated` for each of 12 joints);
- outcome summary (ordered terminal outcome and the summary metrics);
- data-bound plots (fixed plot set carrying run ID, source hashes, and point count).

This task makes the P1-02 contract *runnable*; it does not itself produce formal
Acceptance evidence.

## Fail-closed requirements

- Any missing, stale, malformed, wrong-run, non-finite, or inconsistent runtime
  field makes the episode `INVALID`; never fill with safe-looking defaults.
- Telemetry/event clocks must be finite, non-negative and monotonic; `NaN`/`Inf`
  classifies `INVALID` and validation never raises for these artifact values.
- A collision/fall telemetry `false→true` edge requires the matching structured
  event; an unpaired edge or a safety terminal with `SUCCESS` is `INVALID`.
- Absent or non-finite 11-ray or 5×12 vector elements make the episode `INVALID`.

## Cadence and source-mode capture requirement

- Actual policy/RA/Recovery cadence and the active ray source mode may be claimed
  only from an authoritative runtime capture, never from static config inference.
- Static values (e.g. `update_rate`, `decimation`, `FPS`) and startup log echoes are
  not measured cadence and must not be recorded as measured periods.
- Without an authoritative capture, cadence and active source mode remain `UNKNOWN`.

## Acceptance requirements

P1-09 may be submitted for Acceptance review only when:

- every in-scope schema field has an authoritative runtime producer or an explicit
  `UNKNOWN` with its search boundary;
- structured safety events originate from one authoritative source, not text logs;
- fail-closed handling rejects missing/non-finite/inconsistent fields;
- a representative episode can be classified `VALID`/`INVALID` by the P1-02
  validator without running a benchmark, pilot, or formal Acceptance run;
- legacy evaluator outputs remain `LEGACY / NON-ACCEPTANCE` and P1-01 `UNKNOWN` is
  unchanged;
- cadence and ray source mode are captured at runtime or remain explicit `UNKNOWN`;
- no benchmark, pilot, formal Acceptance, or real-robot result is claimed;
- offline mechanical tests pass and an independent Reviewer can reproduce them.

Acceptance is not automatic from passing mechanical tests. Only the independent
Reviewer may accept P1-09.

## Independent Reviewer requirements

- each runtime source is authoritative (not a proxy, filename, comment, or static
