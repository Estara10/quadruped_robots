# P1-09 — Runtime Source Connection to the Formal Contract

Status: **EXECUTING — P1-09A read-only field-source audit and interface design only**

P1-09A is the first read-only evidence and interface-design increment of P1-09.
It produces the field-to-runtime source map and an adapter-interface note; it makes
no code changes and authorizes no runtime adapter implementation. Runtime adapter
implementation becomes authorized only when the Director opens a later
implementation increment.

## Objective

Connect authoritative runtime sources to the already-accepted P1-02 formal
contract (`abs-go2-formal-run/v1`), so that a future formal episode can bind every
required field to a real runtime producer rather than a fixture or `UNKNOWN`:

- run identity (`run_id`, schema version, wall-clock time, Git commit/branch/dirty
  state or dirty patch hash);
- effective config (snapshot + canonical hash, runtime-effective confirmation);
- seed lineage (root seed and every downstream random source, derived or
  explicitly `UNKNOWN`);
- simulation time (monotonic `simulation_time_s`, sequence, `telemetry_fresh`);
- ray source/mode and 11 rays (active `MUJOCO_RAY_SOURCE`, v2 header validity);
- structured safety events (controller active, RL entered, Recovery ENTER/EXIT,
  collision START/END, fall, arrival, timeout, invalidation, shutdown);
- 5×12 command chain (`action_raw`, `action_clipped`, `joint_target_rad`,
  `torque_nm`, `torque_saturated` for each of 12 joints);
- outcome summary (ordered terminal outcome and the summary metrics);
- data-bound plots (fixed plot set carrying run ID, source hashes, and point count).

This task makes the P1-02 contract *runnable*; it does not itself produce formal
Acceptance evidence.

## Planning vs implementation

This plan separates planning from implementation:

- **Planning (this file)**: define scope, out-of-scope, minimal entrypoints,
  fail-closed rules, Acceptance, and Reviewer requirements. No code changes.
- **Implementation (future, only after Director moves P1-09 to READY)**: add the
  runtime adapter/telemetry/event/plot producers against the P1-02 contract, plus
  offline mechanical tests. Implementation is not authorized by this file.

## Scope (future implementation)

1. Map every P1-02 schema field to an authoritative runtime producer or record it
   `UNKNOWN`, extending [`field_to_runtime_source.md`](../evidence/P1-02/field_to_runtime_source.md)
   with the actual capture point.
2. Add a runtime adapter that emits run-bound manifest/telemetry/events/summary/plots
   for a single episode without running a formal benchmark.
3. Emit structured safety events from one authoritative event source; text logs are
   diagnostic only and never the event source.
4. Enforce fail-closed validity: missing, stale, malformed, wrong-run, non-finite,
   or inconsistent runtime fields classify the episode `INVALID`.
5. Capture effective config snapshot/hash, seed lineage, simulation time, ray
   source/mode and v2 ray header, 11 rays, 5×12 command chain, and outcome.
6. Produce the fixed data-bound plot set with run ID + source hashes.

## Allowed instrumentation boundary

To satisfy the objective, P1-09 implementation is permitted to make minimal
runtime adapter/instrumentation changes — and only those — needed to emit or
capture:

- formal run identity;
- telemetry (including simulation time and sequence);
- structured safety events;
- effective config snapshot/hash (read-only capture, no behavior change);
- seed lineage;
- ray source mode and v2 ray header validity;
- 11 rays and the 5×12 command chain;
- outcome summary and data-bound plots.

Such changes are observational/additive only; they must not alter any control
output.

## Out of scope

- Any change to control semantics, policy inputs/outputs, thresholds, gains,
  switching logic, solver behavior, dynamics, or runtime config behavior.
- Any ROS2, MuJoCo, benchmark, pilot, formal Acceptance run, or real-robot execution.
- Converting legacy evaluator outputs into formal `VALID` evidence.
- Changing Roadmap, Acceptance criteria, Phase status, or P1-01/P1-02 implementation.
- Resolving P1-01 provenance, policy order, RA binding, or foot-force semantics.

## Required boundaries for legacy data

- Existing evaluator outputs (`run_abs_eval.py`, `analyze_abs_eval.py`) remain
  `LEGACY / NON-ACCEPTANCE`; they are not passed to the validator as `VALID`.
- P1-01 `UNKNOWN` values remain unchanged and are recorded as `UNKNOWN`, never
  silently converted to `PASS` or a schema failure.

## Fail-closed requirements

- Any missing, stale, malformed, wrong-run, non-finite, or inconsistent runtime
  field makes the episode `INVALID`; never fill with safe-looking defaults.
- Telemetry/event clocks must be finite, non-negative and monotonic; `NaN`/`Inf`
  classifies `INVALID` and validation never raises for these artifact values.
- A collision/fall telemetry `false→true` edge requires the matching structured
  event; an unpaired edge or a safety terminal with `SUCCESS` is `INVALID`.
- Absent or non-finite 11-ray or 5×12 vector elements make the episode `INVALID`.

## Cadence and source-mode capture requirement

- Actual policy/RA/Recovery cadence and the active ray source mode may be claimed
  only from an authoritative runtime capture, never from static config inference.
- Static values (e.g. `update_rate`, `decimation`, `FPS`) and startup log echoes are
  not measured cadence and must not be recorded as measured periods.
- Without an authoritative capture, cadence and active source mode remain `UNKNOWN`.

## Acceptance requirements

P1-09 may be submitted for Acceptance review only when:

- every in-scope schema field has an authoritative runtime producer or an explicit
  `UNKNOWN` with its search boundary;
- structured safety events originate from one authoritative source, not text logs;
- fail-closed handling rejects missing/non-finite/inconsistent fields;
- a representative episode can be classified `VALID`/`INVALID` by the P1-02
  validator without running a benchmark, pilot, or formal Acceptance run;
- legacy evaluator outputs remain `LEGACY / NON-ACCEPTANCE` and P1-01 `UNKNOWN` is
  unchanged;
- cadence and ray source mode are captured at runtime or remain explicit `UNKNOWN`;
- no benchmark, pilot, formal Acceptance, or real-robot result is claimed;
- offline mechanical tests pass and an independent Reviewer can reproduce them.

Acceptance is not automatic from passing mechanical tests. Only the independent
Reviewer may accept P1-09.

## Independent Reviewer requirements

The Reviewer must independently verify:

- each runtime source is authoritative (not a proxy, filename, comment, or static
  config echo) and links to the exact capture point;
- fail-closed `INVALID` handling for missing/non-finite/inconsistent fields;
- safety-first outcome ordering against the P1-02 schema;
- cadence and ray source mode are captured, not statically inferred;
- legacy outputs and P1-01 `UNKNOWN` remain separated from formal evidence;
- no hidden behavior change, benchmark, pilot, or real-robot execution.

## Stop conditions

- Stop and escalate if connecting a source would require changing controller,
  policy, threshold, or solver semantics.
- Stop and record `UNKNOWN` if a required field has no authoritative producer.
- Stop before any benchmark, pilot, formal Acceptance, or real-robot run.
