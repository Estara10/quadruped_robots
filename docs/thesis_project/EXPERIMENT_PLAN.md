## 1. 当前研究口径与实验目标

接受频繁、反向切换为正常运行现象，不预设有害，不将证明有害作为下一步的前置工作。切换次数和Recovery占比用于解释双阈值、最小保持的作用，不能单独代表方法更好。当前主要看安全完成、碰撞、超时、推进及耗时。

后续顺序见[下一阶段规划](designs/R1/PLAN.md)：先读现有M3碰撞和超时；有依据后才在少量开发图调整一个变量；发现值得验证的效果后再用新图确认。本轮没有执行这些分析和新运行。原480项的冻结指标、选参历史和结果不因当前口径改变而改写。

比较 A/B/C/D 四种策略切换方式在复杂静态障碍环境中的：

- 切换稳定性；
- 风险出现后的响应；
- 避障与任务完成能力；
- 时间和速度代价。

## 2. 场景

- 稀疏障碍：验证基本触发、Recovery 和返回 Agile；
- 中等障碍：观察连续风险和边界附近切换；
- 密集障碍：观察安全、超时和 Recovery 占用的权衡。

现有 PPT 和历史场景只是候选。S6 通过小规模预实验选择最终场景，不额外建设庞大的场景治理系统。

## 3. 核心指标

### 切换行为描述

- 总切换次数；
- 短时间内反向切换次数；
- 相邻切换间隔；
- Recovery 单次持续时间和总占比。

### 安全响应

- RA 满足进入条件到 Recovery 模式的延迟；
- Recovery 动作实际生效延迟；
- 碰撞、跌倒和人工/系统安全中止。

### 任务表现

- 成功、碰撞、跌倒、超时；
- 到达时间；
- 平均速度和必要峰值速度。

切换次数减少但碰撞、延迟或超时恶化时，不能认定为改进。

## 4. 已完成的开发实验与后续边界

T1/T2开发选参已经完成。下列用途是开发实验的通用说明，不代表需要重新执行。后续优化版本单独标记，不替代原A/B/C/D；具体是否做及改哪个变量由现有失败分析决定。

预实验用于：

- 确认四组实现和指标可用；
- 选择阈值差、保持时间和短时窗口；
- 确认场景可达且具有区分度；
- 确定正式重复次数、超时和无效 run 规则。

参数选择以足够解释研究问题为目标，不进行无意义的穷举网格。预实验不并入正式统计。

## 5. 正式仿真

- 在同一场景的两个重复区组内依次安排 A/B/C/D，使用同一reset/起立流程并保存cycle0实测初态；只有实际受控的随机源才报告种子配对，调度种子不代表物理初态相同；
- 固定模型、观测、控制频率、目标和终止规则；
- 每组完成预先约定的重复次数；
- 保存足够计算核心指标的原始时间序列和运行结果；
- 明确记录失败、异常和被排除的 run；
- 正式批次开始时记录 Git commit、模型版本和主要配置；只对关键模型按需记录 hash。

## 6. 单次正式 run 的最小记录

- 组别与切换参数；
- 场景、初始条件/种子和目标；
- 实际 policy 频率；
- RA、模式、位姿、速度、动作和关键障碍输入时间序列；
- 切换、碰撞、跌倒、到达、超时或安全中止；
- 最终结果与耗时。

不要求为每个文件建立 manifest，也不要求复杂 artifact 链。

## 7. 进入正式仿真的条件

- 四组进入、退出和保持行为经过最小功能验证；
- 关键 observation/action 接口与频率正确；
- 核心指标能够从一次试运行中算出；
- 场景、参数、重复次数和排除规则已在正式数据产生前确定。

## 8. 实机验证

实机只做代表性、低速、静态、人工监控的验证。开始前必须确认站立与映射、急停、速度/动作限制、异常停止和真实障碍输入。

实机不要求复制全部 A/B/C/D 仿真矩阵。选择最有解释价值的基线和改进方案，验证实际延迟、切换和避障表现即可。任何明显人身或设备风险未解决时保持 NO-GO。

## 9. 数据保留与复核

- 正式实验及计划用于论文的挑战批次，保留原始策略记录、关键控制/事件日志、终局、上下文、配置、版本、台账和分析结果，至少到论文及答辩主要复核结束。
- 优先无损压缩或转移备份。只有确认归档可读取且内容足够后，才另行讨论移除源副本；备份与删除须作为独立操作明确授权。
- 先清理可重建缓存、重复资源、临时overlay和非必要截图，避免优先删除不可重建的时间序列。GitHub只保存已跟踪文件；被忽略的logs不会因Git提交自动备份。
- 缺失记录须明确列出。现有指标可支持已报告结果，但不能由汇总表补造原始帧，也不能以新运行冒充原记录。
- `manual_map_view.py`可继续用于人工观看并按现有方式清理临时数据；人工观看不作为正式定量证据。
