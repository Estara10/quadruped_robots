# 毕业设计项目总览

> 项目：面向复杂障碍环境的四足机器人风险驱动安全策略切换方法研究  
> 当前基线：已通过答辩的开题报告  
> 建立日期：2026-10-06；状态更新：2026-11-09

## 1. 项目目标

在 Unitree Go2、MuJoCo 和 ROS 2 平台上，构建由 RA Value 驱动的 Agile/Recovery 安全运动闭环，研究滞回和 Recovery 最小保持时间对策略切换稳定性、安全响应和任务完成能力的影响，并获得能够支撑本科毕业论文的仿真与代表性低速实机结果。

项目目标是把毕业设计完整做出来，不是建设工业级安全认证、软件供应链审计或通用实验平台。

## 2. 核心研究问题

接受频繁、短时反向切换是现有策略的正常运行现象，不预设有害，也不要求先证明有害。以下是当前研究安排，不追改原开题材料或已完成实验的指标。

1. 在这种正常切换存在时，双阈值对碰撞、到达、超时、推进和耗时有什么影响？
2. 最小保持时间带来哪些实际收益和代价，是否限制了必要的任务推进？
3. 两种机制组合后是否产生额外收益，或者出现过度驻留等代价？
4. 哪些场景和参数条件下有可复现的实际收益，哪些属于现有策略能力边界？

切换次数、短反向和Recovery占比作为行为描述与解释，不单独作为方法有效性的判据。R1已完成M3失败分析、M2历史对照及多批开发比较。R1-11结果仍是有限线索，不能确认B普遍改善，见[报告](evidence/R1/AB_TWO_CANDIDATES_120/分析报告.md)。A/C保持研究先后完成旧280项批次（含保留的第29项SYSTEM_SAFETY_ABORT）和独立120项三图确认批次。新批120/120实际启动并有有效记录，到达32、碰撞58、仿真限时29、墙钟保护1；H=0.02呈现有限、地图特定的重复线索，H=0.10/0.12未稳定重复既有改善，仍无法确定代表H。新旧批次分别报告，challenge08长保持退化继续保留为限制；详情见[120项结果报告](evidence/R1/AC_HOLD_CONFIRM_120/20261101_r1_ac_hold_confirm_120/RESULTS_SUMMARY.md)和[研究计划](designs/R1/PLAN.md)。R1相关历史批次分别报告，当前任务阶段与下一步见本页当前状态和R1任务页。

## 3. A/B/C/D 研究设计

| 组别 | 滞回 | Recovery 最小保持 | 用途 |
|---|---:|---:|---|
| A | 否 | 否 | 原始单阈值基线 |
| B | 是 | 否 | 检验滞回的独立作用 |
| C | 否 | 是 | 检验最小保持的独立作用 |
| D | 是 | 是 | 检验组合效果 |

主要比较为 B−A、C−A、D−B 和 D−C。除两个研究因素外，模型、观测、控制频率、场景、目标、初始条件和终止规则应尽量保持一致。

## 4. 技术闭环

环境与机器人状态 → Agile 正常运动 → RA 风险评估 → A/B/C/D 切换器 → Recovery 避障/恢复 → 返回 Agile → 指标记录 → 仿真对照 → 低速实机验证 → 论文结果。

必须优先确认的接口只有：observation/action 维度、joint/action order、单位、实际 policy 频率、RA 输入输出、阈值语义、保持时间和仿真/控制器接口。

## 5. 范围

### 必做

- A/B/C/D 四种切换机制；
- 稀疏、中等、密集静态障碍仿真；
- 切换稳定性、安全响应和任务表现指标；
- 参数预实验与正式配对仿真；
- 仿真结果与失败案例分析；
- 通过安全准备后的代表性低速实机验证；
- 论文所需数据、图表和复现说明。

### 有余力再做

- 超出R1条件验证规模的更多随机布局、动力学扰动、感知来源对比；
- 更细的参数敏感性或交互效应分析；
- 自动化论文图表。

### 默认不做

- 为非关键文件建立 hash/manifest 链；
- 穷尽历史 UNKNOWN 或恢复旧模型训练环境；
- 工业级 fail-closed、watchdog、故障注入和层层审批；
- 为追求论文极限速度而牺牲稳定性与可解释性；
- 与论文问题无关的平台扩张。

## 6. 最小充分验证

每一步采用“目标 → 实现 → 最小验证 → 记录结论 → 下一步”。验证只需要足以证明功能满足下一阶段需要：

- 接口问题：证明维度、顺序、单位和频率正确；
- 切换机制：证明进入、退出、保持和边界行为正确；
- 仿真实验：证明控制变量、重复次数和指标足以回答研究问题；
- 实机阶段：重点防止人员受伤和设备损坏。

只有不解决就无法进入下一步、会使实验无法解释、会造成明显实机风险或会偏离开题报告的问题，才是 BLOCKER。其余归为 MAJOR、MINOR、TECHNICAL DEBT 或 OPTIONAL。

## 7. Reviewer 与问题分级

Reviewer 只重点判断：功能是否真实实现、验证是否足够、问题是否影响论文结论、是否存在明确实机风险、是否允许进入下一步。

不得仅因为缺少非必要 hash/manifest、工作树存在无关历史修改、旧 P1 未闭环、历史 UNKNOWN 未清空或普通仿真缺少工业级冗余而拒绝当前任务。

问题只按以下方式处理：

- **BLOCKER**：阻止下一步、使实验无效、造成明显实机风险或偏离开题报告；
- **MAJOR/MINOR**：需要修正但不必无限扩大当前任务；
- **TECHNICAL DEBT**：记录，等实际影响主线时再处理；
- **OPTIONAL**：有余力再做。
