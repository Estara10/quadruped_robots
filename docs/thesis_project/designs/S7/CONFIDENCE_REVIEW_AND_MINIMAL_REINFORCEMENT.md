## 1. 核心判断

已较有把握：四组配置与状态机、C/D保持时钟/入口/退出语义、最新批次周期记录及终止后排空，均有定向验证和真实运行支持。

最需要补强的不是继续调阈值，而是：**新定义的“安全任务完成”能否在真实记录上保持一致、可解释的分类，以及工程失败和未知值是否改变组间比较。** 下列是准备风险排序，不代表已经独立审计出缺陷。

## 3. 建议的最小实施范围（待另行授权）

1. 优先执行第1、2项，复用现有开发数据，不碰留出集，不新增仿真。
2. 在运行器准备时同时处理这两项，不创建第二个Active Task或独立补强大项目。
3. 第3项先只读分析，不要求完全相同初态或完整消费遥测作为正式实验前必达门槛；只有实质异常才升级。
4. 第4项属于案例与结论边界，默认不修改感知和模型；不能因正式D表现不佳重新调参。
5. 新增离线检查、代码修改或开发场景运行须由后续执行提示明确授权；今天仅写计划。若无具体异常，不扩大检查矩阵、追加模型训练或重复参数扫描。

## 4. 正式方法保护

已审阅通过的方法、参数和240项顺序不因补强而按成绩调整。若补强发现改变主指标含义/执行语义的真实缺陷，先报告方法修订，再冻结，不能将不同代码阶段悄悄混成一批。

必须同时报告：已确认安全到达、到达但安全未定、竞争终局、工程无效、站立/关闭状态；分母与UNKNOWN情景公开。足端事件不被默认为不存在，base_link界内不代表整机足迹，接口输出不代表消费。

四组正式优劣本来就是待回答的问题，不能为了增加信心继续用开发数据证明D必胜。保留独立留出验证的价值。
