# D435i 原生补洞候选离线对照

## 问题与范围

用替换机同一批 9 张 Z16 深度帧比较：A) 原始零值替换 6 m；B) librealsense 2.58.4 mode 1 的源码算法后，剩余零值替换 6 m。两种输入使用相同模型、160×90中心采样、0.1–6 m裁剪、`log2(m)`及三通道复制。输出仅用于输入敏感性诊断，不代表测距精度或控制安全。未修改原始帧、模型、严格适配器、共享内存协议或控制器。

数据均来自新相机 `238322070866` 的三组数据，每组3帧；文件为480×270、小端uint16，记录比例尺0.001 m/单位。帧文件不自带内参和曝光参数，这些仍以原采集记录为准。

## SDK 版本和 mode 1 含义

本机安装 `ros-humble-librealsense2` 2.58.4。官方 2.58.4 C++ API 把 mode 1 叫作 `farest_from_around`，文档语义是从邻像素中选离相机较远的值；该版本的[滤波实现](https://github.com/realsenseai/librealsense/blob/v2.58.4/src/proc/hole-filling-filter.cpp)先复制输入帧，再处理副本。[版本固定的算法头文件](https://github.com/realsenseai/librealsense/blob/v2.58.4/src/proc/hole-filling-filter.h)对 Z16 的具体循环则是：只填内部零像素，按行从上到下、每行从左到右原地扫描，以五个索引位置（上、左上、左、左下、下）中的最大值写入；顶、底、最左边界不填。扫描过程中刚填入的值可被后续像素再次使用。因此实现可能把连续未知区逐步传播填满，填入值不都来自原始直接邻居。

官方 [API Changes](https://github.com/realsenseai/librealsense/wiki/API-Changes)列出 mode 1 的“最远邻居”概念；2.51.1发布说明没有记录此滤波实现变更，但可取得的2.51.1版本说明不包含其内部像素循环。故**不能证明2.51.1与2.58.4逐像素算法相同**；本报告的B只代表2.58.4版本固定源码算法候选。尝试用2.58.4软件设备帧调用安装SDK时，运行阶段报 `could not initialize udev monitor`，未执行到滤波输出；未打开相机。为完成有限离线比较，分析脚本按上述2.58.4固定源码逐步实现了uint16循环，并明确标为源码等价计算，未伪称SDK运行时实测。

## 视场合同

当前微调模型的训练清单列出 `mujoco_ray_pred_medium_20260611` 与 `mujoco_ray_pred_near_20260611`；两份数据清单均明确记录 `camera_hfov_deg=102.0`（[medium数据清单](../../../ABS/training/legged_gym/legged_gym/depth_data/mujoco_ray_pred/mujoco_ray_pred_medium_20260611/manifest.json)、[near数据清单](../../../ABS/training/legged_gym/legged_gym/depth_data/mujoco_ray_pred/mujoco_ray_pred_near_20260611/manifest.json)、[模型微调清单](../../../archive/ray_pred_finetune/mujoco_finetune_soft_safety_20260611/manifest.json)）。训练数据生成器把 `CAMERA_HFOV_DEG=102°` 用作MuJoCo虚拟深度相机的渲染视场；训练标签由独立几何射线计算，11束角度固定为−45°至+45°、步长9°（[`compare_ray_pred.py`](../../../scripts/compare_ray_pred.py#L42)、[标签计算](../../../scripts/compare_ray_pred.py#L304)、[渲染器](../../../scripts/compare_ray_pred.py#L346)、[数据生成器](../../../scripts/generate_mujoco_ray_dataset.py#L151)）。因此102°不是射线标签角度范围，也不是实时推理的角度变换参数。

当前相机记录的水平视场约88.9°。适配器只是把480×270中心采样为160×90，没有裁剪或视场重映射（[`realsense_depth_to_abs_rays.py`](../../../scripts/realsense_depth_to_abs_rays.py#L81)）。按理想针孔近似，训练时±45°方向落在约第15和145列；88.9°视场下±45°会落在约−2和162列，刚在画面之外，其余角度对应的像素位置也会偏移。故不是把图拉伸即可补齐的问题：若要对齐，需要用相机视场重新生成/筛选输入和几何标签，或用相机视场匹配的数据重新训练并验证；本轮未训练。三组帧没有随帧CameraInfo，88.9°仅为已有相机记录的近似值。

## ABS输入处理结论与下一步

当前共享内存每帧只传11个有限浮点距离，没有逐束有效位图；控制器根据帧头和时龄校验整帧。若深度发布端保留原始未知掩码，可在未知程度达到经已知目标验证的拒绝条件时，不刷新整帧射线时间戳，让现有时龄校验走既有整帧失效路径（[`abs_ray2d_shm_contract.h`](../../../common/abs_ray2d_shm_contract.h#L8)、[`StateRL.cpp`](../../../quadruped_ros2_control_humble/controllers/rl_quadruped_controller/src/FSM/StateRL.cpp#L1043)）。目前没有可据以指定的未知比例阈值；由于模型由全图输入共同预测，初始核查应覆盖完整160×90模型输入，并记录11束输出变化。后续应以已知位置/距离的前方障碍测出阈值与拒帧代价，不能靠2m、6m等占位语义推出安全。

帧超时触发的是项目现有 `safetyVeto`/PASSIVE 路径；它不等于已验证的机器人制动或稳定停止。mode 1加6 m只作为诊断候选，不应直接接控制。**值得进行一次静态、只读射线观察**，但目的应是：在Orin实际2.51.1 SDK上，对同一帧保存原始掩码、mode 1新增掩码、剩余未知及A/B射线，并用少量固定且实测距离/方向的障碍记录对照；不发布共享内存、不控制机器人。这样同时核实现场SDK实际像素循环和观察输出敏感性。视场训练合同与未知值的控制策略仍需另行解决后，才能讨论在线接入。
