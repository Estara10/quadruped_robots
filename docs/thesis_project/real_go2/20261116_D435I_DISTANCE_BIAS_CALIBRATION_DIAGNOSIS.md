# D435i 距离偏差与校准诊断（2026-11-16）

> 后续进展：下文为当时只读诊断记录。之后操作者在PC Viewer完成On-Chip比较及Tare并报告保存；原配置1m/2m复测满足用户±2%阶段标准。当前状态以[校准与复测报告](20261116_D435I_TARE_AND_DISTANCE_CHECK.md)为准，不再沿用本文“尚未运行Health Check”的历史状态安排工作。

## 结论

现有数据呈现距离越远、原始深度偏高越明显：约50cm时 +0.2cm；约106.5–107cm时 +3.3–3.8cm；约149–150cm同位置两次分别 +6.2–7.8cm；约200cm组为 +11cm，但黑胶带与红十字是否同点未确认。它支持存在稳定、近似随距离增长的偏差，不足以区分双目视差/标定误差、低分辨率模式影响和参考点差异，也不能据此拟合修正系数。

已复核的单位换算、补洞、中心测点及 Z 到欧氏距离差不解释该趋势。此次 SDK 只读快照未发现明显异常的深度单位或高级参数，但“参数看起来正常”不能证明标定正确。

## 官方自校准诊断边界

已检查安装的2.51.1头文件和固定版本 [`src/rs.cpp`](https://github.com/realsenseai/librealsense/blob/v2.51.1/src/rs.cpp)：`run_on_chip_calibration`调用底层校准并返回候选表/Health Check；单独的`set_calibration_table`用于设置当前动态表，`write_calibration`才写入EEPROM/Flash。官方说明进一步指出，运行On-Chip后ASIC会在当前会话启用新表，但不会自动写Flash；候选表可以在验证后保留或丢弃。[官方自校准说明](https://dev.realsenseai.com/docs/intel-realsense-self-calibration-for-d400-series-depth-cameras/)

因此本轮**没有运行Health Check，也没有生成候选表**：运行接口本身会暂时改变当前会话使用的校准，超出本轮“不应用候选标定”的边界。没有调用`set_calibration_table`、`write_calibration`、Tare或修改Depth Scale；Flash未写入。SDK示例会切换到256×144@90，并改动发射器/曝光相关选项，但本轮未照搬这些改动。

即使未来得到Health Check，它衡量的是算法定义的校准健康/重标定需求，不是绝对距离误差验收。官方建议D435/D455使用标准On-Chip模式；场景需有足够纹理，快速变化纹理、移动场景或发亮表面会降低Health Check可靠性。自校准属于微调，不替代完整工厂标定。官方调优资料指出D435推荐848×480，低分辨率会降低深度精度；这使当前480×270成为值得区分的候选因素，但不证明其造成了本次距离比例偏差。[官方深度调优说明](https://dev.realsenseai.com/docs/tuning-depth-cameras-for-best-performance/)

## 判断与唯一下一步

**下一步只做一次固定目标的分辨率对照**：相机和柜面目标保持不动，在同一测点先用现有480×270@60，再用设备支持的848×480@10采集短段原始深度；两档都记录相同中心/邻域原始Z、profile、scale、曝光/增益、投射器值和时间。尽量复用已确认的149–150cm红十字位置，不重新拟合距离修正值；若无法确认目标和相机未移动，则这次对照不用于定量判读。此对照能判断远距离偏差是否明显依赖采集分辨率，不能单独验证标定健康或绝对精度。

若分辨率对照仍保持相近比例偏差，之后再由主助手决定是否授权“运行On-Chip并允许当前会话临时启用候选表”的前后对照；届时须明确如何恢复已备份的原始表或重启恢复Flash表。当前没有安全依据直接应用或写入候选校准。
