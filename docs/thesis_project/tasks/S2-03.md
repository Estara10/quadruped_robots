## 已定位的问题

`scripts/s1_run_diagnostic.py` 的 `publish()` 在每次发布时新建 shell、加载 ROS 环境并执行 `ros2 topic pub --once`，`monotonic_ns` 在 subprocess 返回后才读取。终局后的 PASSIVE 停止也使用这一路径。

原两次 terminal 到发布函数返回分别约 1.8134 s、1.4855 s；这些是包括调用准备和发布退出的总间隔，不能说成实际 DDS 发送延迟。机器人在此期间仍有策略输出。

另有两个记录问题：
- `STRATEGY_STOP_CONFIRMATION` 只搜索普通 FSM 的 `Switched from ... to passive`，实际 command 1 走 GLOBAL HARD STOP 分支，日志形式不同。false 不能直接解读为控制器没有转 PASSIVE。
- `output_after_request_duration_ns=250000000` 是固定等待常量，不是实际观察到的策略持续输出时间。须去掉这类冒充测量的字段含义。

### 1. 接触对象及规则核对

复核两个 run 的目标、实际模型、具名接触对象及运动窗口。解释检测到的是脚/小腿与障碍的短接触，而不是自动判定为明显撞击。

保持当前研究诊断的“机器人-障碍 contact 即碰撞终局”规则，不改成忽略脚接触、不加任意持续时间过滤，不改模型碰撞 margin。若发现实际分类错误，只修正可证实错误。

为本次新证据补充最小可解释字段：接触 geom ID/具名部位、障碍位置或可解析身份、物理步/仿真时间；优先利用已有数据。若要区分 margin 接触与穿透，检查并记录可取得的 contact distance，说明 MuJoCo 接触激活语义。缺少距离/力的历史记录明确 UNKNOWN，不反推。

### 2. 及时发送停止

在 RL 开始前建立并核对可复用的 ROS 发布通道，终局时直接发布 PASSIVE，避免终局路径才启动 CLI、加载环境和等待发现。保持现有 control_input 的 command 1 语义，不改 A 切换器或模型。

终局确定后尽快请求停止；必要终止快照持久化保持完整，昂贵报告生成、进程清理及分析放在停止请求之后。初始化失败、记录失败和操作员中止也必须可靠收尾。预建发布通道失败时不请求 RL。

分别记录：终局观察、停止调用开始、发布调用返回、控制器收到请求/完成 PASSIVE 转换（有证据才写）、进程退出。时间全部准确注明来源，不能把发布返回叫物理停止。

停止确认必须对应本次 controller、终局后的请求和实际 hard-stop 路径。必要时在该生产分支完成 PASSIVE 转换后增加最小确认日志；不能把发出请求或转换前日志当完成确认。不要求建设 MuJoCo command-ID 消费确认系统。

### 3. 分离运动与收尾观察

终止帧仍是运动指标终点。保留短时、单独标明 cleanup 的观测，用于判断终局后策略是否仍推进、机器人是否继续移动；这些数据不得混入到达时间、路径或成功统计。

移除固定 250 ms 假测量。没有采到停止确认或末次策略输出时，记录 UNKNOWN/有界观测范围。停止失败时立即走有界的本次进程清理，不继续追目标。

最终终端摘要增加：结束原因、结束时距目标距离、接触部位/对象（适用时）、停止确认和清理结果，避免用户把窗口关闭误认为到达。

### 4. 最小验证

允许生产路径针对性离线检查，覆盖预建发布、终局立即发出停止、hard-stop 确认归属、超时/中止/异常清理、终止帧完整性和 cleanup 指标排除。必要增量构建。

允许最多一次有界的当前 A 配置短仿真补证，沿用场景/模型/阈值/目标 (7,0)，6 仿真秒运动上限、60 s 墙钟保护；不重复直到成功、不追求必须碰撞。正常停止事件即可核对时序；没有接触时使用历史接触证据，不人为修改 RA 或碰撞。

显示/OpenGL、唯一 writer/session 和新发布通道预检通过后才启动 RL；使用此前已授权的沙箱外桌面权限，不安装组件或修改系统授权。关键失败后不自动重跑。

证据必须能区分：停止请求及时发出、controller 停止策略输出、物理惯性运动、MuJoCo 实际消费命令 UNKNOWN。分别报告实测延迟与观测范围，不承诺零延迟或零位移。
